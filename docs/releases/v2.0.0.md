# v2.0.0

## Release Summary

Version `v2.0.0` extends the reference implementation from one Fabric solution to
several, deployed by a single Azure DevOps pipeline that only touches the
solutions a commit actually changed.

Article 01 promoted one solution through `develop`, `release`, and `main`. That
design does not survive a second team sharing the repository: copying the
pipeline per solution means every fix is made three times, and keeping one
pipeline that deploys everything means an unrelated notebook edit republishes
another team's production workspace.

This release keeps the promotion model unchanged and adds change detection on
top of it. Three solutions, nine workspaces, one framework.

## Features

- Change detection that maps a git diff onto solution folders
- One deployment engine parameterised by solution and environment
- Reusable Azure DevOps stage and step templates, instantiated per solution
- Central solution registry holding workspace IDs by variable name, never by value
- Scoped deployments: the repository root is rejected as a source path
- Empty-source guard: a solution folder with no items aborts before any Fabric call
- Shallow-clone detection, so a missing diff baseline fails loudly instead of silently skipping
- Manual `solutionsOverride` parameter for deliberate framework rollout
- Offline test suite requiring neither Azure, Fabric, nor pytest

## Breaking Changes

Upgrading from `v1.0.0` is not a drop-in replacement.

| Change | Action required |
| ------ | --------------- |
| Solution artifacts move under `fabric-workspaces/<Solution>/` | Move artifacts; reconnect Fabric Git integration to the new folder |
| Deployment script moved to `scripts/deploy_fabric_workspace.py` | Update the pipeline script path |
| `REPOSITORY_DIRECTORY` no longer defaults to the repository root | Set it per solution, or let the registry resolve it |
| New required environment variable `SOLUTION_KEY` | Pass it from the pipeline |
| New required file `config/solutions.yml` | Create the registry |
| Workspace ID variables are now solution-qualified | Rename `UAT_WORKSPACE_ID` to `VED_UAT_WORKSPACE_ID` and add one per solution |
| Detection requires full git history | Add `fetchDepth: 0` to the detection checkout |

When moving folders, disconnect Fabric Git integration **before** moving them.
Moving a folder underneath a live connection makes Fabric see its items as
deleted.

## Tested Deployment Path

Verified end to end against three Fabric solutions and nine workspaces:

| Branch | Detected | Result |
| ------ | -------- | ------ |
| `develop` | one solution changed | that solution validated against DEV; the other two skipped |
| `release` | one solution changed | that solution deployed to UAT; the other two skipped |
| `main` | all three changed | all three deployed to PROD; every DEV and UAT stage skipped |

Detection was also verified against real Fabric commits for each solution
individually, including item names containing spaces.

## Prerequisites

- Azure DevOps project and repository
- Fabric Development, UAT, and PROD workspaces per solution
- A service principal with workspace access on every target workspace
- Variable groups for the three environments, with solution-qualified workspace IDs
- Python 3.9 or later for local validation

## Known Limitations

- No `parameter.yml` is included. Items referencing a workspace-specific resource
  by GUID will still point at the source environment after deployment.
- No approval gates. A merge to `main` deploys PROD unattended.
- A push of several commits at once is evaluated from `HEAD~1`, so only the last
  commit is inspected. Promotion happens through pull requests, where the full
  change set is visible, so this affects direct pushes to `develop` only.
- Warehouse schema deployment remains intentionally excluded.
- `LOG_LEVEL=INFO` produces a `fabric-cicd` warning on the first line of every
  deployment log; only `DEBUG` is currently supported by the library.
